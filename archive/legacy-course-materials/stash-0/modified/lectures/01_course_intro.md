# 01 MotrixLab 的定位与使用边界

## MotrixLab 是什么

MotrixLab 是一个面向机器人强化学习任务的工程框架，用来组织环境、仿真、训练、奖励、配置、注册、日志和 Demo 分析。

它不是单个 Demo 集合，也不是只封装一个 RL 算法的训练脚本。

> 核心理解：Demo 是入口，不是全部。长期需要阅读、修改和扩展的是环境、奖励、配置和训练流程。

## 机器人强化学习任务的工程复杂度

普通 RL 教学任务通常比较小，例如 `CartPole`、`Pendulum` 这类环境。机器人任务复杂得多，因为它同时涉及物理系统和学习系统。

常见组成：

- **机器人模型**：`URDF` / `MJCF` / `XML` 等模型文件
- **关节和执行器**：动作最终要映射到可执行的控制量
- **物理仿真**：接触、碰撞、动力学、仿真步进
- **控制频率**：`sim_dt`、`ctrl_dt` 等时间尺度
- **观测空间**：智能体每一步能看到什么
- **动作空间**：策略网络输出代表什么
- **奖励函数**：行为好坏如何转成训练信号
- **终止条件**：成功、失败、超时、摔倒、越界等
- **训练算法**：PPO 等算法如何采样和更新
- **日志和权重**：训练过程如何保存、复现和评估

这些内容如果放在一个脚本里，很快会失控。MotrixLab 的价值在于把这些部分拆成相对清楚的模块。

## 平台核心价值

机器人强化学习项目里，真正难维护的通常不是单个公式，而是工程组织。

MotrixLab 主要解决以下问题：

- **环境定义**：任务目标、观测、动作、`step`、`reset` 如何组织
- **奖励设计**：多个奖励项如何计算、组合、调权重
- **配置管理**：仿真参数、任务参数、训练参数如何集中管理
- **注册机制**：框架如何通过环境名找到对应配置和环境实现
- **训练入口**：命令行参数如何进入 `Trainer`、`Env` 和 RL 配置
- **Demo 分析**：如何用统一方法拆解一个已有任务

模块职责可以理解为：

```text
环境模块 -> 定义任务
奖励模块 -> 生成学习信号
配置模块 -> 管理参数
注册模块 -> 建立名字到实现的映射
训练入口 -> 串联任务、配置、算法和日志
```

## 典型使用场景

### 学习和教学

用已有任务理解机器人 RL 项目的基本拆分方式。重点看环境如何写、奖励如何设计、配置如何生效、训练如何启动。

### Demo 复现和分析

先跑通官方 Demo，再拆解任务目标、观测、动作、奖励、终止条件。不能只看 Demo 能不能运行，还要看它为什么能运行。

### 任务改造

在已有任务上改奖励项、目标位置、动作尺度、终止条件或训练超参。适合做 A/B 实验和小范围功能验证。

### 新任务开发

基于已有 `EnvCfg`、`Env`、`Reward`、`registry` 的模式，注册新的环境名和配置类。重点是复用框架约定，不要把逻辑散落到临时脚本里。

## 阅读 MotrixLab 的推荐顺序

不要一开始就逐行读所有代码。先建立模块地图，再进入具体文件。

推荐顺序：

1. 先找入口脚本：`train` / `play` / `view` 相关脚本
2. 再看注册系统：环境名如何映射到 `EnvCfg`、`Env`、`RLCfg`
3. 再看 `EnvCfg`：任务和仿真参数在哪里定义
4. 再看 `Env`：动作如何进入环境，仿真如何推进，观测如何返回
5. 再看 `Reward`：奖励项如何计算和组合
6. 最后看 RL 配置：`num_envs`、`rollouts`、`learning_rate`、网络结构等训练参数

排查问题时也按这个顺序缩小范围：

- **跑不起来**：先看入口参数、注册名、模型路径
- **环境创建失败**：看 `EnvCfg`、`registry`、依赖后端
- **动作没效果**：看动作映射、控制接口、仿真层
- **reward 异常**：看状态读取、奖励项、权重和终止条件
- **训练不收敛**：综合看观测、动作、奖励、PPO 超参和并行规模

## 本阶段学习主线

前四章只建立第一条主线：

```text
MotrixLab 能做什么
-> 框架怎么分层
-> EnvCfg / Env / Reward 如何协作
-> Reward 为什么影响训练结果
```

后续再继续看：

- 配置系统：默认值、继承、覆盖、实验参数管理
- 注册系统：`env` 名称如何绑定配置和实现
- 训练流程：命令行到 `Trainer`，再到环境和算法
- Demo 分析：任务目标、观测、动作、奖励、终止条件、可复用设计

> 一句话：学习 MotrixLab 时，先看工程组织，再看代码细节；先判断模块职责，再判断具体实现是否合理。
