# 02 MotrixLab 基础框架：分层架构

## 四层结构

MotrixLab 可以按四层理解：

- 用户接口层
- 训练算法层
- 环境实现层
- 物理仿真层

这四层从上到下协作。用户接口层接收命令，训练算法层负责策略学习，环境实现层定义任务，物理仿真层负责底层物理状态推进。

```text
用户接口层
训练算法层
环境实现层
物理仿真层
```

> 读代码时先判断文件属于哪一层，再看它承担什么职责。

## 用户接口层：训练入口与命令行参数

用户接口层是使用者最先接触到的部分，常见形式是 `train.py`、`play.py`、`view.py` 这类入口脚本。

主要职责：

- 读取命令行参数
- 确定 `env_name`
- 选择训练后端或仿真后端
- 处理 `num_envs`、`seed`、`render`、`policy` 等运行参数
- 组装 `cfg_override` 或 `env_cfg_override`
- 创建 `Trainer` 或直接创建环境
- 启动 `train` / `play` / `view` 流程

这一层不应该承载大量任务逻辑。如果在入口脚本里堆了很多奖励、观测、动作处理代码，说明职责可能混乱。

排查方向：

- **命令行参数传错**：看用户接口层
- **env 名称不存在**：看入口参数和注册系统
- **后端选择异常**：看 `train_backend` / `sim_backend` 的传递路径
- **num_envs、seed 没生效**：看 override 是否真正传给 `Trainer` 或 `registry.make`

## 训练算法层：策略学习与 RL 后端

训练算法层关注如何训练策略，不关心机器人任务的语义细节。

典型职责：

- 创建 `policy` / `value` 网络
- 采集 `rollout`
- 计算 `advantage`
- 计算 `policy loss`、`value loss`、`entropy loss`
- 执行 `optimizer step`
- 保存 `checkpoint`
- 记录训练日志

MotrixLab 中训练算法层可能对接不同后端，例如 `skrl`、`rslrl`，或不同 backend，例如 `jax`、`torch`。对上接收训练配置，对下和环境交互。

训练算法层需要环境提供标准 RL 信息：

- `observation`
- `action`
- `reward`
- `done` / `terminated` / `truncated`
- `info`

要点：

- PPO 不理解机器人真实目标，只优化环境返回的 `reward`。
- 算法层不应该直接依赖某个机器人模型文件。
- 同一个环境可以使用不同 RL backend，但需要有对应的 `RLCfg` 注册。

排查方向：

- **loss 或 KL 异常**：看 PPO 超参、学习率、`rollout`、batch 设置
- **checkpoint 没保存**：看训练器和日志目录
- **torch / jax 切换失败**：看 backend 专用 `RLCfg` 是否存在
- **reward 上升但任务失败**：优先看环境和奖励，不要只改算法层

## 环境实现层：任务逻辑

环境实现层是机器人 RL 任务的核心，定义这个任务到底是什么。

通常包含：

- `EnvCfg`：环境参数
- `Env`：环境流程
- `Reward`：奖励计算
- `reset` 逻辑
- `observation` 构造
- `action` 处理
- `termination` 判断

环境实现层负责回答：

- 智能体看到了什么
- 智能体能输出什么
- 动作如何作用到机器人
- 一步之后状态如何变化
- 当前行为得多少 `reward`
- episode 什么时候结束

常见问题大多发生在这一层：

- 观测缺少任务关键信息
- 动作尺度不合理
- 奖励方向写反
- 奖励项量级失衡
- 终止条件太严或太松
- `reset` 后初始状态不合理

排查方向：

- **训练曲线完全不动**：看 `reward` 是否稀疏、观测是否有效
- **策略输出没效果**：看动作映射和控制接口
- **行为很奇怪**：看 reward 漏洞、动作惩罚、终止条件
- **环境随机崩**：看 `reset`、仿真参数、状态维度

## 物理仿真层：机器人状态推进

物理仿真层负责让机器人在模拟世界中运动。

主要内容：

- 模型加载
- 关节、执行器、传感器
- 接触、碰撞、摩擦
- 质量、惯性、几何体
- 仿真步长 `sim_dt`
- 控制步长 `ctrl_dt`
- 动力学积分

这一层的问题通常表现为：

- 机器人一开始就抖动
- 穿模、爆炸、飞走
- 接触不稳定
- 控制输入和实际动作不一致
- 仿真速度或频率异常

不能把所有仿真异常都归因于 PPO。如果物理系统本身不稳定，训练算法只能在不稳定环境上优化。

排查方向：

- 初始状态是否合法
- 模型文件路径是否正确
- 关节范围、质量、惯性是否合理
- `sim_dt` / `ctrl_dt` 是否匹配
- 动作是否超过执行器能力
- 接触参数是否导致不稳定

## 一次训练的调用链

典型流向：

```text
用户命令
-> 入口脚本解析参数
-> 根据 env_name 找注册项
-> 加载 EnvCfg / RLCfg
-> 创建环境
-> 创建 Trainer / Agent
-> 策略输出 action
-> Env 接收 action
-> 仿真层推进状态
-> Env 构造 observation / reward / done
-> 算法更新策略
-> 日志和 checkpoint 保存
```

这个链路可以作为读代码的主线。不要孤立看某个类，要看它在链路中负责哪一步。

## 分层排查表

| 问题 | 优先检查 |
| --- | --- |
| 入口命令报错 | 用户接口层，确认 `env`、`backend`、`num_envs`、`seed`、`policy` 等参数 |
| 环境名找不到 | `registry`，确认 `@envcfg` / `@rlcfg` / env 实现是否注册 |
| 环境创建失败 | `EnvCfg` 默认值、模型路径、仿真 backend 和构造函数 |
| 训练能跑但 reward 异常 | `Reward`、`Env` 状态读取、奖励项量级和 `done` 条件 |
| 机器人动作异常 | `Env` 的动作处理和物理仿真层控制接口 |
| 训练不收敛 | 先看观测、动作、奖励，再看 PPO 配置 |

## 基本原则

读 MotrixLab 时先分层：

- 入口负责启动
- 算法负责学习
- 环境负责任务
- 仿真负责物理

修改代码时也按层修改：

- 不要在训练脚本里硬写任务逻辑。
- 不要在算法层塞机器人语义。
- 不要把可调参数散落在 `Env` 内部。
- 不要把物理不稳定问题简单归结为 `reward` 或 `learning_rate`。
