# 04 奖励函数：任务目标的工程表达

`Reward` 是强化学习任务的学习信号。算法不会直接理解任务意图，只会优化环境返回的 `reward`。

要点：

- PPO 不知道真实目标。
- PPO 只知道 `observation`、`action`、`reward`、`done`。
- 如果 `reward` 表达错了，算法会认真优化错误目标。

## 奖励函数在训练循环中的位置

强化学习基本循环：

```text
智能体观察环境
-> 策略输出 action
-> Env 执行 action
-> 物理仿真推进状态
-> Env / Reward 根据状态计算 reward
-> 算法根据 reward 更新策略
```

`Reward` 输入通常包括：

- 当前状态
- 上一步动作或当前动作
- 目标位置 / 目标速度 / 任务条件
- 接触信息
- 姿态、速度、关节状态
- episode 进度
- `EnvCfg` 或 `reward_config` 中的权重

`Reward` 输出通常包括：

- scalar reward
- 分项 reward
- success / failure 指标
- debug 信息

> 训练时不要只看总 reward。要看 reward 分项、success rate、episode length、termination reason 和行为视频。

## 奖励设计原则

### 目标一致

`reward` 必须和任务目标一致。如果任务是抓取，不能只奖励靠近物体；如果任务是行走，不能只奖励速度而忽略稳定性。

### 信号密度

复杂机器人任务通常不能只靠稀疏成功奖励。只在成功时给 `1`、其余为 `0`，早期随机策略很难获得有效反馈。

需要中间信号，例如距离变近、姿态更稳、速度更接近期望。

### 尺度合理

不同 reward 项量级要可比较。

- 如果动作惩罚远大于成功奖励，模型可能学会不动。
- 如果速度奖励远大于稳定性惩罚，模型可能学会抖动或摔倒前冲。

### 方向明确

奖励项之间可以平衡，但不能严重互相抵消。一个项鼓励高速，另一个项强惩罚速度，需要明确权重设计目的。

### 防止漏洞

策略会利用 reward 的表达缺陷。

- 奖励末端速度，可能学会抖动刷分。
- 奖励接近目标，可能贴近但不完成任务。
- 奖励某个姿态指标，可能用非预期姿势满足指标。

### 可解释

每个 reward 项都应该能说明它服务哪个任务目标。无法解释的 reward 项会增加调参难度。

## 常见奖励结构

| 奖励项 | 作用 |
| --- | --- |
| 目标接近奖励 | 用于 reach、grasp、navigation 等任务，给策略提供持续方向 |
| 成功奖励 | 任务完成时给额外奖励，强化最终目标 |
| 稳定性奖励 | 用于平衡、行走、机械臂姿态控制 |
| 动作平滑惩罚 | 惩罚 action 过大或变化过快，减少抖动 |
| 能耗惩罚 | 惩罚力矩、功率、关节速度或控制成本 |
| 失败惩罚 | 摔倒、碰撞、越界、掉落、任务失败时给负奖励或终止 episode |
| 时间相关奖励 | 鼓励更快完成任务，或稳定维持任务状态 |

## 加权组合

机器人任务 reward 通常是多个项的加权和。

典型结构：

```text
total_reward =
    task_reward
    + success_bonus
    + stability_reward
    - action_penalty
    - energy_penalty
    - failure_penalty
```

设计顺序：

1. 先定义最终任务目标
2. 再加入能引导探索的中间奖励
3. 加入必要的稳定性和安全约束
4. 检查每个 reward 项的数值范围
5. 训练后看分项曲线和行为视频

不要只凭总 reward 判断 reward 是否合理。总 reward 上升，可能只是某个辅助项变高。

## 常见问题

### 奖励太稀疏

- **现象**：训练曲线长期没有明显变化，成功率接近 0。
- **原因**：随机探索很难碰到成功状态。
- **处理**：加入距离、姿态、速度等中间反馈。

### 奖励方向错误

- **现象**：模型越训越偏离真实目标。
- **原因**：reward 优化方向和任务目标不一致。
- **处理**：逐项检查 reward 的符号和目标含义。

### 惩罚过大

- **现象**：策略保守，机器人不动或动作很小。
- **原因**：动作成本、碰撞惩罚、失败惩罚主导总 reward。
- **处理**：检查惩罚项量级和成功奖励强度。

### 辅助奖励主导

- **现象**：总 reward 上升，但任务没有完成。
- **原因**：模型刷高了辅助项，例如速度、稳定、接近，但没有达成主目标。
- **处理**：看 success rate 和 reward breakdown。

### 奖励漏洞

- **现象**：机器人出现非预期但高 reward 的行为。
- **原因**：reward 指标没有完整约束任务。
- **处理**：通过视频观察行为，补充约束项或调整终止条件。

### 终止条件干扰奖励

- **现象**：episode 过短，模型无法探索；或异常状态持续刷分。
- **原因**：done 条件太严或太松。
- **处理**：reward 和 termination 一起检查。

## 排查顺序

训练失败时，优先检查 reward：

1. reward 是否和任务目标一致
2. reward 是否有足够密集的学习信号
3. 每个 reward 项符号是否正确
4. 每个 reward 项量级是否合理
5. 是否某个辅助项主导 total reward
6. 是否存在 reward 漏洞
7. termination 是否配合 reward
8. success rate 是否和 total reward 同步变化

同时检查 observation 和 action：

- reward 再合理，如果 observation 缺目标信息，策略也很难学。
- reward 再合理，如果 action 没有正确作用到机器人，训练也不会成功。

## 调试建议

### 记录 reward 分项

不要只输出 `total_reward`。至少记录 `task_reward`、`success_bonus`、`action_penalty`、`failure_penalty` 等关键项。

### 看行为视频

reward 曲线不能替代行为观察。特别是 reward 上升但任务没完成时，视频最容易暴露漏洞。

### 做小实验

先固定简单初始状态，先降低随机性，先用较短任务验证 reward 方向，再逐步增加随机性和任务复杂度。

### 检查边界状态

成功边界、失败边界、超时边界、重置边界都要看。很多 reward bug 出现在边界状态。

## 基本原则

`Reward` 是任务目标写进代码后的形式。它不是注释，也不是讲解，而是算法真正优化的对象。

奖励设计要做到：

- 目标一致
- 信号足够
- 尺度合理
- 分项可解释
- 行为可验证
- 防止漏洞

> 一句话：强化学习算法优化的是你写出来的 reward，不是你心里想的目标。
